SECTION 06

§6　実践設計② 生徒同士のレビューをプルリクエストで回す

「読んで感想を言い合いましょう」は、たいてい「いいと思いました」で止まります。 プルリクエストを使うと、感想が「ここを、こう直したら?」という具体的な提案に変わり、 受け取る側には採用・棄却を理由つきで決める仕事が生まれます。

使いどころ: 探究レポートの相互レビュー、班の共同文書、生徒会・部活の文書づくり。

使う機能: ブランチ＋プルリクエスト＋行コメント（すべてブラウザ操作）

6-1

仕組みを1分で

1

ブランチ

本体を汚さない下書きコピー。提案はまずここに書く。

2

プルリクエスト

下書きを「こう直したら?」の提案書として送る。理由を添える。

3

レビューと決定

受け取った側が行単位でコメントし、採用(Merge)か棄却(Close)を理由つきで決める。

sync_alt
これはSLOW AIの「返す」の実装です。AIと違って、隣の生徒は誤解し、反論し、思いがけない角度から提案してきます。そのずれが具体的な差分として目に見える——「いいずれだね」を道具が支えてくれます。決定権が書き手に残る(勝手に書き換えられない)ことも、行為主体感の設計としてそのまま使えます。
6-2

手順　提案する側（レビュワー生徒）

  1. 相手のリポジトリ（Collaboratorとして招待されている前提）で、対象のファイルを開く
  2. 鉛筆マークで編集画面に入り、直したい箇所を書き換える
  3. Commit changes で 「Create a new branch for this commit and start a pull request」を選ぶ——ここが本体を直接書き換えないための分かれ道
  4. 提案の説明欄に「どこを・なぜ」を書いて Create pull request
提案文の型（生徒に配る） クリックでコピー
## あなたの文章をこう読みました （相手の意図を一文で復唱。ずれていたら教えて） ## 提案 （どこを・どう変えたか） ## 理由 （なぜその方が良くなると思ったか。根拠や出典があれば添える）
6-3

手順　受け取る側（書き手の生徒）

  1. リポジトリの Pull requests タブを開き、届いた提案を見る
  2. Files changed で、変更箇所が赤(削除)と緑(追加)で並ぶのを確認。気になる行には行番号の＋からコメントできる
  3. 納得したら Merge pull request（採用）。納得できなければコメントで理由を書いて Close（棄却）
  4. どちらの場合も理由を一言残す——採用・棄却の判断こそが学習の本体です
6-4

授業での回し方（50分の型）

  • 0-10分: 書き手がREADMEまたはレポート.mdを最新にコミット
  • 10-30分: ペアで相互に1件ずつプルリクを送る（提案文の型を使う）
  • 30-45分: 受け取った提案に行コメント→採用/棄却を理由つきで決める
  • 45-50分: 「相手の提案で一番『いいずれ』だったもの」を口頭で共有
  • 先生は Pull requests の一覧を見るだけで、誰がどんな提案をし、誰がどう判断したかを全部あとから見取れます
favorite
レビューの作法を先に配る。①相手の意図を復唱してから提案する ②人ではなく文に向ける ③直す案がないなら質問でよい。この3つを§7のルールとセットで配ると、プルリクが「あら探し」にならず回ります。

ワーク — 先生同士でプルリクを1往復

隣の人と、§4で作ったリンク集リポジトリにお互いをCollaborator招待→相手のREADMEに提案を1件送る→受けた提案を採用または棄却(理由つき)まで(15分)。生徒にやらせる前に、この1往復を自分の体で通しておくのが一番の準備です。
